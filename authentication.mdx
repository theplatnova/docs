Every server-to-server call to the Platnova Business API is authenticated with your **API key**, sent in the `X-API-Key` header.

## Get your API key

Create a key in your dashboard under [Settings → Developers](https://business.platnova.com/settings/developer). Keys work only once your business is live; until then calls that move money answer `403 entity_not_active` (see [Going live](/going-live)).

To start building before then, [get sandbox keys](https://sandbox.business.platnova.com): signing up for the sandbox takes an email and a password, with no verification (see [Environments](/environments#sandbox)).

## Key prefixes

A key says which environment it belongs to:

| Prefix | Environment | Base URL |
|---|---|---|
| `pk_test_` | Sandbox | `https://sandbox.api.platnova.co` |
| `pk_live_` | Live | `https://api.platnova.com` |

Keys made before prefixes start `api_key_` and keep working where they were made.

A key sent to the other environment is refused with `401` and a `data.code` that says so, before anything else is checked:

```json
{
  "status": false,
  "data": { "code": "sandbox_key_on_live" },
  "error": ["sandbox_key_on_live"],
  "message": "This is a sandbox API key (pk_test_). Send it to https://sandbox.api.platnova.co, or use a pk_live_ key here."
}
```

| `data.code` | Meaning |
|---|---|
| `sandbox_key_on_live` | A `pk_test_` key was sent to live |
| `live_key_on_sandbox` | A `pk_live_` key was sent to the sandbox |

## Send it in `X-API-Key`

```bash
curl https://api.platnova.com/v1/wallets \
  -H "X-API-Key: YOUR_API_KEY"
```

That is the only supported way to send an API key.

<Warning>
- **Do not send your API key as `Authorization: Bearer ...`.** `Authorization` is for dashboard sessions; an API key there is refused with `401 un-authorized access`.
- **Do not send a dashboard session token alongside your API key.** A request that carries both is treated as the signed-in dashboard user, not your integration. On `POST /v1/checkout` that turns a sale into a top-up of your own wallet (see [Initiating Checkout](/checkout/initiating-checkout)).
- **Do not put the key in the URL.** The query parameter `api_key` still works on some routes but is **deprecated** (since 22 October 2026) because URLs end up in proxy, CDN and browser logs. Partner routes already refuse it.
</Warning>

## Keep the key secret

- Keep it on your server. Never put it in a browser, a mobile app or a public repository.
- Store it in an environment variable or a secrets manager.
- If a key may have leaked, create a new one in the dashboard and delete the old one.
- Check your dashboard regularly for activity you don't recognise.
- [Verify webhook signatures](/webhooks/signatures) before acting on an event.

## Failed authentication

A missing, unknown or deleted key answers `401` (a key for the other environment answers `401` with a code; see [Key prefixes](#key-prefixes)):

```json
{ "status": false, "data": {}, "error": [], "message": "un-authorized access" }
```

## Rate limits

Some routes are rate limited per client IP per minute (for example payment creation on a checkout). A throttled call answers `429` with the message `please wait for few minutes, try again later`, and these headers:

| Header | Meaning |
|---|---|
| `X-RateLimit-Limit` | Calls allowed per minute on that route |
| `X-RateLimit-Remaining` | Calls left in the current minute |
| `X-RateLimit-Reset` | Unix time when the window resets |

Back off until `X-RateLimit-Reset` before retrying.
