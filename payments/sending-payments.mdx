Send money transfers using multiple payment methods. This guide covers how to send payments and track their status.

## Sending a Payment

Send a payment by specifying the payment method and recipient details in `info`. Example for a bank transfer:

```bash
curl -X POST https://api.platnova.com/v1/payments/send \
  -H "X-API-KEY: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "from_amount": 500.00,
    "from_wallet_id": "43a2b75e-5c59-429e-872a-2a54c7b17e37",
    "to_currency": "NGN",
    "payment_method": "bank_transfer",
    "info": {
      "account_number": "0123456789",
      "bank_code": "058",
      "account_name": "Jane Smith"
    },
    "reference": "INV-2026-0042",
    "payment_type": { "type": "instant" }
  }'
```

## Payment Parameters

### Required Fields

- **from_amount** – Amount to send (source currency)
- **from_wallet_id** – Wallet ID to debit from
- **to_currency** – Destination currency (e.g. NGN, USD)
- **payment_method** – One of: `bank_transfer`, `card`, `mobile_money`, `wallet`, `tag_transfer`, `defi`, `revolut`, `paypal`, `cashapp`, `zelle`
- **info** – Recipient details; required fields depend on `payment_method` (e.g. for `bank_transfer`: `account_number`, `bank_code`, `account_name`; for `tag_transfer`: `tag_id`)

### Optional Fields

- **reference** – Your own unique id for this payment, such as your invoice or payout id. Strongly recommended. Each reference can be used once: a second send with the same reference is refused, so the same payment is never sent twice. You can look the payment up by it with [Verify Payment](/payments/verification).
- **payment_type** – `instant`, `scheduled`, or `recurring` (default: instant)
- **is_save_to_beneficiary** – Save recipient as beneficiary

## Finding the bank_code

`bank_code` is not a CBN or SWIFT code; it is the code our payment provider uses for that bank in that country. Get it from [List banks](/api-reference/banks/list) for the recipient's country, and use it as-is:

1. `GET /v1/banks/{country_code}` lists every bank with its `code`.
2. For Ghana and Kenya, `GET /v1/banks/{country_code}/{bank_code}` lists branches; pass the chosen `branch_code` in `info.branch_code`.
3. `POST /v1/banks/verify` resolves the account number to the holder's name before you send.
4. If you only have an account number, `POST /v1/banks/suggest` returns banks we have paid it through before.

Cache the bank list for at most a day. All four endpoints need your API key.

## Payment Response

```json
{
  "status": true,
  "data": {
    "transaction_ref": "BTRNSF7HeRoy4CRl6hcOOqAzwAeo0WLLMMbtQ2",
    "status": "pending",
    "from_amount": 500,
    "to_amount": 500,
    "from_currency": "ngn",
    "to_currency": "ngn",
    "method": "bank_transfer",
    "created_at": "Tuesday, 3 November, 09:15"
  },
  "error": [],
  "message": "operation was successful"
}
```

`transaction_ref` is Platnova's unique reference for the payment. Store it next to your own `reference`; either one works with Verify Payment.

## Duplicate references

Sending a `reference` you already used is refused with `400`, and nothing is sent. `data.transaction_ref` is the payment that already has that reference:

```json
{
  "status": false,
  "data": { "code": "duplicate_reference", "transaction_ref": "BTRNSF7HeRoy4CRl6hcOOqAzwAeo0WLLMMbtQ2" },
  "error": [],
  "message": "duplicate transaction detected: reference already exists"
}
```

If two sends with the same reference arrive at the same time, one runs and the other waits for it, then gets this refusal. A reference is never paid twice.

## Payment Status

Payments are processed asynchronously. Check a payment with `POST /v1/payments/verify`, using either the `transaction_ref` or your own `reference`:

```bash
curl -X POST https://api.platnova.com/v1/payments/verify \
  -H "X-API-KEY: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "reference": "INV-2026-0042"
  }'
```

- `success`: paid. Final.
- `failed`, `cancelled`, `reversed`: not paid; the money is back in your wallet. Final.
- `pending`, `processing`, `pending_approval`, `under_review`: not decided yet. Check again later, or wait for the `transfer.success` / `transfer.failed` webhook.

Treat anything other than `success` as not paid. See [Verifying a payment](/payments/verification#response-a-payout) for the full response.

## Handling timeouts

If your send request times out, you don't know whether the payment was created. Don't send a new payment with a new reference; use your reference to find out:

<Steps>
<Step title="Send with your own reference">
Always pass a unique `reference` to `POST /v1/payments/send`, and store it before you send.
</Step>
<Step title="On a timeout, verify by your reference">
Call `POST /v1/payments/verify` with `{"reference": "<your reference>"}`.
</Step>
<Step title="Found: use the answer">
The payment exists. `data.ref` is its `transaction_ref` and `data.status` says where it is. Don't send it again.
</Step>
<Step title="Not found: resend with the same reference">
`400` with `data.code` `payment_not_found` means the payment was never created. Resend it with the **same** `reference`. If the first send turns out to have gone through after all, the resend is refused with `duplicate_reference` and its `transaction_ref`, and nothing is paid twice.
</Step>
</Steps>

Any other error from verify (for example `something went wrong, please contact support`) does not mean "not found": verify again before resending.

### With an `Idempotency-Key`

You can also send an `Idempotency-Key` header with every payout. After a timeout, retry with the **same key and the same body**: if the first request finished you get its answer and nothing is sent again, and if it is still running you get `409 request_in_progress` (wait for `Retry-After`). Or look it up with [`GET /v1/payments/by-key/{key}`](/api-reference/payments/by-key): `payment.ref` is the `transaction_ref` you missed, and `nothing_created: true` means nothing was sent. See [Retrying safely](/errors#retrying-safely).

## Payment Methods

The API supports multiple payment methods; pass `payment_method` and the matching `info` shape:

| Method | Description | Example info fields |
|--------|-------------|---------------------|
| **bank_transfer** | Bank transfers (NGN, USD, etc.); ACH, RTP, wire for USD | `account_number`, `bank_code`, `account_name` |
| **card** | Card payments | Card-specific recipient details |
| **mobile_money** | Mobile money (e.g. Ghana) | Phone, provider, etc. |
| **tag_transfer** | Wallet-to-wallet transfer | `tag_id` |
| **wallet** | Wallet payments | Wallet identifier |
| **defi** | DeFi | Asset, network, address, etc. |
| **revolut** | Revolut | Revolut recipient details |
| **paypal** | PayPal | PayPal identifier |
| **ussd** | USSD | USSD channel details |
| **cashapp** | Cash App | Cash App identifier |
| **zelle** | Zelle | Zelle recipient details |

Availability depends on currency and region. See the [Send Payment API](/api-reference/payments/send) for the exact `info` fields per method.

## Payment Limits

Payment limits may apply based on:

- Account tier
- Currency
- Payment method
- Regulatory requirements

## Payment Fees

Fees may apply depending on:

- Payment amount
- Currency
- Payment method
- Destination country

## Best Practices

- Verify recipient account details before sending
- Send a unique `reference` with every payment, and verify by it after a timeout
- Monitor payment status regularly
- Keep sufficient wallet balance
- Handle failed payments appropriately
