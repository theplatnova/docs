The API answers with standard HTTP status codes and one of three JSON shapes. Branch on the **HTTP status** first, then on `data.code` when it is present. `message` is written for a person; don't parse it.

## Response shapes

### 1. Standard response (most success and error answers)

```json
{
  "status": false,
  "data": { "code": "request_in_progress" },
  "error": [],
  "message": "This request is still being processed. Nothing new was done."
}
```

- `status` is a **boolean**: `true` for 2xx, `false` otherwise.
- `data` holds the result on success. On some errors it holds a machine-readable `code` and details (for example `data.missing` on `entity_not_active`). It is `{}` when there is nothing to add.
- `error` is an array, usually empty.

### 2. Validation failure (HTTP 422)

A body that is missing a required field or has a field of the wrong type:

```json
{
  "status": "error",
  "message": "Validation failed",
  "errors": {
    "amount": ["This field is required"],
    "email": ["This field is required"]
  }
}
```

<Warning>
In this shape `status` is the **string** `"error"`, not a boolean, and the details are in `errors` (plural), keyed by field. Treat any HTTP 422 as a validation failure regardless of the body.
</Warning>

### 3. Rate limited (HTTP 429)

```json
{ "status": false, "data": {}, "error": [], "message": "please wait for few minutes, try again later" }
```

with `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` headers (see [Authentication](/authentication#rate-limits)).

## Status codes

| Status | Meaning | Retry? |
|---|---|---|
| `400` | The request was refused. Read `message` and `data.code`. Nothing was done. | Not unchanged; fix the request |
| `401` | Missing or invalid API key (`un-authorized access`). | No; fix the key |
| `403` | Not allowed: the business is not live (`entity_not_active`), or the key or user lacks permission. | No |
| `404` | Not found (for example a checkout older than 7 days). | No |
| `409` | A request with the same `Idempotency-Key` is still running (`request_in_progress`). Nothing new was started. | Yes, with the **same** key, after the `Retry-After` header (seconds) |
| `413` | Request body too large (`request_too_large`). | No |
| `422` | Validation failed (shape 2), or an `Idempotency-Key` reused with a different body. | No; fix the request |
| `429` | Rate limited (shape 3). | Yes, after `X-RateLimit-Reset` |
| `5xx` | Our error. The outcome of a money request may be unknown. | Yes, **with the same `Idempotency-Key`** so it can't run twice |

## Error codes

| `data.code` | Status | What it means | What to do |
|---|---|---|---|
| `entity_not_active` | 403 | Your business is not live yet. `data.missing` lists what is left. | Finish [going live](/going-live) |
| `idempotency_key_required` | 400 | This route requires an `Idempotency-Key` and none was sent. | Send one |
| `idempotency_key_invalid` | 400 | The key is not 1–255 of letters, digits, `_`, `.`, `:`, `-`. | Fix the key |
| `idempotency_key_reused` | 422 | The key was already used for a different request. | Use a new key for a new request |
| `request_in_progress` | 409 | The first request with this key is still running. | Retry with the same key |
| `idempotency_unavailable` | 503 | We couldn't start the request. Nothing was sent. | Retry with the same key |
| `request_too_large` | 413 | Body over the size limit. | Send less |
| `line_items_invalid` | 400 | `line_items` don't add up to `amount`, or a line is invalid. `message` says which. | Fix the lines |

Refunds have their own codes; see [Refunds](/checkout/refunds).

### Common messages without a code

| Message | Status | Where |
|---|---|---|
| `currency is not supported for checkout` | 400 | `POST /v1/checkout` |
| `invalid success_url` / `invalid cancel_url` | 400 | `POST /v1/checkout`: send an absolute `http(s)` URL |
| `checkout not found` | 404 | `GET /v1/checkout/{id}` |
| `payment not found` | 400 | `POST /v1/payments/verify`: not paid yet, or not your payment |
| `something went wrong, please contact support` | 400/500 | Unexpected failure; include the time and your reference when contacting support |

## Retrying safely

Send an `Idempotency-Key` on every request that creates or moves money. Then a retry after a timeout, a `5xx` or a `409` either returns the first answer or runs once, never twice. See [Making retries safe](/checkout/initiating-checkout#making-retries-safe-idempotency-key).
