Receive real-time notifications for card activity, virtual account funding, and payment transfers by configuring webhooks in your [dashboard](https://business.platnova.com). Events are sent as **POST** requests to the URL you configure.

## How Webhooks Work

1. **Configure your endpoint**: in the dashboard, set the URL that will receive webhook events (it must be `https` and publicly reachable; see [Endpoint URLs](/webhooks/delivery#endpoint-urls)) and choose the events you want. You can supply a secret, or leave it blank and we generate one. Either way, the secret is shown **once**, when the endpoint is created. Store it then.
2. **Receive events**: we send a POST request to your URL for each subscribed event. Answer with any **2xx** status within 30 seconds to acknowledge it.
3. **Verify every call**: check the `X-Platnova-Signature` header against the raw body with your secret. See [Verifying webhooks](/webhooks/signatures).
4. **Retries and recovery**: each event gets 3 attempts (the first plus 2 retries). An endpoint that keeps failing is paused, and you are emailed. It resumes by itself once it answers again, and nothing recorded in the meantime is lost. See [Delivery, retries and pausing](/webhooks/delivery).

<Warning>
We judge a delivery by your HTTP status alone. Any 2xx means delivered, and that event is never sent again. If your signature check fails, answer with a non-2xx status such as `401`, not `200` with an error in the body.
</Warning>

## Request Details

| Property | Description |
|----------|-------------|
| **Method** | `POST` |
| **URL** | The endpoint URL you configure in the dashboard |
| **Content-Type** | `application/json` |
| **Headers** | `X-Platnova-Signature` and `X-Platnova-Key-Id` on signed endpoints, plus the legacy plain-text `X-Webhook-Secret` / `X-Auth-Secret` (see [Verifying webhooks](/webhooks/signatures#the-headers-we-send)), and any custom headers you configured |
| **Body** | JSON payload (see event payloads below) |

## Event Payloads

Every webhook payload includes top-level fields:

- **event** – Event type (e.g. `card.created`, `transfer.success`).
- **timestamp** – ISO 8601 timestamp when the event occurred.
- **customer_id** – Customer ID associated with the event (may be empty for entity-level events).
- **data** – Event-specific payload (see below).

### checkout.paid

Sent when a checkout (including one opened from a payment link) is settled. Checkout payers have no customer record, so `customer_id` is empty and the payer's email is in `data.customer_email`.

```json
{
  "event": "checkout.paid",
  "timestamp": "2026-10-10T12:00:00Z",
  "customer_id": "",
  "data": {
    "checkout_id": "checkout_id",
    "link_id": "link_id",
    "reference": "PN-1234567890",
    "amount": 9850.00,
    "paid_amount": 10000.00,
    "fee": 150.00,
    "currency": "NGN",
    "payment_method": "bank_transfer",
    "customer_email": "payer@example.com",
    "status": "success"
  }
}
```

- **checkout_id** – The checkout that was paid.
- **link_id** – The payment link the checkout came from. Omitted when the checkout was not opened from a payment link.
- **reference** – The transaction reference. Quote it to support when asking about this payment.
- **amount** – What you are credited, in `currency`.
- **paid_amount** – What the payer sent. Reconcile the payer's statement against `paid_amount` and your own ledger against `amount`.
- **fee** – The difference between the two: what Platnova kept.
- **payment_method** – One of `bank_transfer`, `tag_transfer`, `crypto`, `card`, `ussd`, `opay`, `bank_account`, `mobile_money`, `apple_pay`, `google_pay`.
- **customer_email** – The email the payer entered at checkout. Omitted when none was given.
- **status** – `success`.

By the time this event is sent, the payment can also be confirmed with [Verify payment](/api-reference/payments/verify) or [Get checkout](/api-reference/checkout/get).

### checkout.failed

Sent when a checkout is not settled, most often because an underpayment is being reversed. Same payload as `checkout.paid`, with `status` set to `failed` and a `reason`.

```json
{
  "event": "checkout.failed",
  "timestamp": "2026-10-10T12:00:00Z",
  "customer_id": "",
  "data": {
    "checkout_id": "checkout_id",
    "reference": "PN-1234567890",
    "amount": 8000.00,
    "paid_amount": 8000.00,
    "fee": 0,
    "currency": "NGN",
    "payment_method": "bank_transfer",
    "customer_email": "payer@example.com",
    "status": "failed",
    "reason": "We received NGN 8000 against an order for NGN 10000. The payment is being returned to the sender and the order has not been settled."
  }
}
```

- **amount**, **paid_amount**, **fee** – What was attempted, not collected. Nothing was settled to you. For a reversed underpayment, `paid_amount` is what arrived and is being returned to the payer, and `fee` is 0.
- **reason** – Why the checkout failed. Written for a person to read; do not parse it.

### defi.payment

Sent as a crypto checkout payment progresses: when the payer's transfer is seen, while it confirms, and when it settles, expires or fails.

```json
{
  "event": "defi.payment",
  "timestamp": "2026-10-10T12:00:00Z",
  "customer_id": "user_id",
  "data": {
    "order_id": "checkout_id",
    "amount": 686.11,
    "fee": 14.00,
    "reference": "BDEP123456",
    "currency": "USD",
    "status": "partially_paid",
    "booking_status": "successful",
    "requested_amount": 689.00,
    "rate": 0.9996,
    "metadata": {
      "pay_address": "TXYZ...",
      "pay_currency": "usdttrc20",
      "order_id": "checkout_id",
      "order_description": "Order #1042",
      "actually_paid_at_fiat": 700.11,
      "payment_id": "5115741345",
      "transaction_hash": "0xabc...",
      "sender_address": ""
    }
  }
}
```

- **amount** – What was credited to you (once settled), in `currency`.
- **fee** – What was kept back: Platnova's fee plus any VAT.
- **status** – The crypto processor's own status for the payment: `waiting`, `confirming`, `confirmed`, `sending`, `partially_paid`, `finished`, `expired` or `failed`. Passed through unchanged.
- **booking_status** – How Platnova booked the payment: `pending`, `successful`, `partially_completed`, `failed`, `cancelled` or `reversed`. **Use this to decide whether an order is paid.** The processor calls any shortfall `partially_paid`, even a payment a few cents short because of a network fee, but Platnova books a payment that covers the invoice as `successful`. `partially_completed` means less arrived than was asked, and `amount` is what did arrive.
- **requested_amount** – The invoice the payer was asked to pay, in `currency`. It includes the fee when the fee is charged on top.
- **rate** – What one coin of `pay_currency` was valued at, in `currency`. On settlement this is the market rate when the payment settled. Before settlement it is the invoice's quoted rate.
- **metadata.actually_paid_at_fiat** – The value of the coins that arrived, at `rate`.
- **metadata.transaction_hash** / **sender_address** – The payer's on-chain transfer and, where the chain shows it (Solana today), the sending wallet. Empty until the transfer is seen.

## Best Practices

- **Verify the signature**: check `X-Platnova-Signature` over the raw body, in constant time, before processing. See [Verifying webhooks](/webhooks/signatures). Endpoints created before 24 September 2026 that are not signed should check `X-Webhook-Secret` until they are.
- **Respond quickly**: return 2xx as soon as you have verified and stored the payload, and process it asynchronously.
- **Handle duplicates**: an event can arrive more than once, and backlogs are redelivered after a pause. Deduplicate on `transaction_ref` or `reference`.
- **Test your receiver**: use **Send test event** in the dashboard to see the status, latency and response body your endpoint returns for a signed call.
- **Log for debugging**: log incoming webhook requests and your responses, so you can troubleshoot delivery and retry issues.

Webhook endpoints are created and managed in the [dashboard](https://business.platnova.com); there is no API-key endpoint for managing them.
